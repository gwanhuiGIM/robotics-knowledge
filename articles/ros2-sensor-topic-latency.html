E2E 지연 = 캡처·전송·큐 대기·처리·판단·제어단 지연의 합. 구성에 따라 단계가 겹치거나 추가된다.

1. 레이턴시의 기본 개념

레이턴시(latency)는 어떤 이벤트가 발생한 시점부터 특정 결과가 관측되는 시점까지의 시간차다. 신호 전파 지연, 처리 지연, 큐 대기 지연 등을 구분해야 한다. 네트워크의 편도 지연(one-way latency), 왕복 시간(RTT), 카메라 노출부터 수신까지의 지연, 센서 입력부터 제어 출력까지의 end-to-end latency는 서로 다른 지표다. 지터(jitter)는 지연의 변동이며, 처리량(throughput)·프레임 레이트(FPS)와도 구별한다.

2. 단일 PC의 ROS 2 센서 경로

RealSense D435i 영상의 경로는 대략 센서 노출 → 카메라 내부 처리/USB 전송 → librealsense/드라이버 → ROS 2 퍼블리시 → DDS 또는 intra-process 전달 → 구독 콜백 → CV/AI 처리 → 판단·제어다. 단일 PC라도 USB, CPU 스케줄링, 메모리 복사, 색 공간 변환, DDS 전달 및 Executor 지연이 있다. CPU가 포화되거나 구독 처리 속도가 발행 속도보다 느리면 메시지가 오래된 상태로 소비될 수 있다. IMU와 이미지의 생성 주기가 다르다는 사실만으로 큐가 반드시 밀리는 것은 아니다.

3. D435i에서 PointCloud 비활성화의 의미

PointCloud 생성 기능을 꺼 놓으면 포인트클라우드 변환·발행에 사용되는 연산과 메모리를 절약할 수 있다. 하지만 depth 이미지 스트림 자체가 자동으로 비활성화되는 것은 아니다. 실제 절감량은 depth/color 스트림 설정, align 단계, 후처리, subscriber 구성에 달려 있다. RGB 1280×720×3바이트 raw 8-bit 영상은 프레임당 약 2.76MB(10진 MB), 30fps면 페이로드만 약 82.9MB/s다. 640×480×3바이트, 30fps면 약 27.6MB/s(약 221Mb/s)로 패킷·미들웨어 오버헤드는 별도다.

4. 한 PC와 두 PC간 통신 비교

동일 PC에서도 노드 간 데이터 이동에는 시간이 걸리며, 두 PC는 추가로 NIC, OS 네트워크 스택, 전송 매체, 스위치/AP, DDS discovery, 패킷 분할·재조립, 손실 및 재전송(전송 방식과 QoS에 따름)의 변수를 가진다. 특히 Wi-Fi는 혼잡·간섭·재전송에 따른 지터가 클 수 있다. 그러나 두 PC를 유선으로 연결하고 작업을 분산해 CPU 병목을 줄이면 전체 센서→판단 지연이 단일 과부하 PC보다 낮아질 수도 있다. 토픽 왕복 RTT와 실제 영상 캡처→의사결정 지연은 별도 측정한다.

5. QoS와 큐 관리

최신성 위주의 카메라 스트림은 sensor-data에 적합한 Best Effort, Keep Last(depth 1~5 등)를 검토할 수 있다. 다만 QoS의 depth=1은 모든 계층의 대기열을 제거하거나 수신 노드가 반드시 최신 프레임을 처리한다고 보장하지 않는다. 실제 콜백 처리 시간, DDS 구현, 드라이버 내부 큐, Executor 구조를 함께 점검한다. IMU depth=10~20도 보편적 정답이 아니며 적분기·동기화기·데이터 손실 허용 여부에 따라 결정한다. 서로 다른 QoS의 호환성도 확인한다.

6. 컴포넌트와 intra-process 통신의 한계

ROS 2 컴포넌트를 같은 프로세스로 구성하고 rclcpp intra-process communication을 켜면 특정 메시지와 API 조건에서 복사와 직렬화 비용을 줄일 수 있다. 모든 구성에서 보장되는 순수 zero-copy나 지연 0ms를 뜻하지는 않는다. Python(rclpy) 기반 처리, cv_bridge 변환, 이미지 인코딩, GPU 메모리 이동 등은 별도 비용이 남는다. 드라이버가 컴포넌트인지 및 사용하는 RealSense ROS wrapper 버전과 구성 지원 여부를 먼저 확인한다.

7. 타임스탬프와 센서 동기화

header.stamp가 무엇을 기준으로 기록되었는지(하드웨어 캡처 시각, 드라이버 시각 등)를 확인하고 각 장치·PC의 시계를 동기화해야 한다. message_filters ApproximateTime은 시간상 가까운 메시지를 묶는 도구이지 전송 지연을 제거하는 기능이 아니다. tf2는 해당 시각의 좌표 변환을 조회하도록 돕지만 실제 데이터가 늦게 도착하는 현상이나 센서간 시계 오차를 자동으로 수정하지 않는다. 다중 PC는 NTP/chrony 또는 필요 시 PTP, 카메라 타임스탬프 설정 등을 고려한다.

8. 측정·개선 절차

① 카메라 노출/메시지 stamp/콜백 진입/추론 종료/제어 발행 시각을 기록한다. ② 동일 PC의 프레임 age, FPS, 드롭률, P50/P95/P99 지연을 측정한다. ③ 유선 LAN과 Wi-Fi에서 같은 시험을 반복한다. ④ raw/compressed 이미지, 해상도·FPS, QoS, callback group/Executor, intra-process 구성별로 비교한다. ⑤ 각 PC의 CPU·GPU·USB·네트워크 사용량을 함께 수집한다. ⑥ 데이터의 처리 위치를 선택할 때는 네트워크에서 raw 이미지를 보내는 대신 엣지에서 인식하고 객체 위치·검출 결과만 전송하는 방안을 비교한다. JPEG 압축은 대역폭을 줄일 수 있지만 인코딩/디코딩 지연과 손실이 있으며 모든 상황에 유리한 것은 아니다.

기존 AI 답변의 주요 정정

원래 주장 요지정정 및 주의점
“인트라 프로세스 사용 시 지연이 사실상 0”잘못된 일반화. 메시지 전달 비용 감소와 end-to-end 지연 0은 다르다.
“PointCloud를 끄면 전체 레이턴시가 크게 준다”조건부. depth/align 등 남은 처리와 실제 PC 병목에 따라 효과가 달라진다.
“IMU·카메라의 주기 차이 때문에 큐가 쌓인다”그 자체로는 원인이 아니다. 수신·처리 속도와 큐/동기화 설정이 핵심이다.
“두 PC 통신은 훨씬 느리다”지연 요인은 늘지만 분산 처리로 end-to-end가 빨라질 수 있다.
“message_filters/tf2로 레이턴시를 보정한다”시간 정렬과 좌표 변환에 도움을 주지만 실제 데이터 전송 지연을 제거하지 않는다.
“Queue depth=1이면 무조건 최신 프레임”계층별 버퍼와 콜백 동작을 고려하면 보장할 수 없다.

ROS 2 + D435i에서 먼저 검증할 것

  1. 실제 활성화된 color/depth/IMU 스트림과 PointCloud 발행 여부를 구분한다.
  2. ros2 topic hz, ros2 topic bw로 토픽 주기·데이터량을 관측하되 도구 측정값과 센서 실제 생성률이 같다고 가정하지 않는다.
  3. 드라이버 타임스탬프 의미와 clock source를 확인하고 처리 노드에서 프레임 age와 콜백 소요 시간을 기록한다.
  4. 기존 구성 → 해상도/FPS 변경 → QoS 조정 → intra-process(지원되는 구성에서) → 유선/무선 분산 구조를 순차 비교한다.
  5. 제어용 토픽은 신뢰성, 데이터 최신성, Deadline 요구조건과 안전 동작을 별도로 검토한다.
