Q1 · 엣지 디바이스 환경

엣지 디바이스(Edge Device) 환경이란?
엣지 디바이스 환경은 데이터를 클라우드나 중앙 서버로 전송해 처리하는 대신, 데이터가 생성되는 현장 가까이에서 직접 수집·연산·분석·제어하는 컴퓨팅 환경을 의미합니다.
로보틱스 관점에서는 로봇에 탑재된 산업용 PC, NVIDIA Jetson, Raspberry Pi 등이 대표적인 엣지 디바이스입니다.
예를 들어, 카메라로 물체를 인식하고 로봇팔을 제어하는 시스템에서 클라우드 서버 없이 로컬 장치에서 YOLO 추론과 ROS 2 노드를 실행한다면 엣지 컴퓨팅 환경에 해당합니다.

4. 로보틱스 프로젝트에 적용한다면

기존에 다뤘던 ROS 2, YOLO, RealSense, LiDAR 기반 시스템을 예로 들면 다음과 같이 구성할 수 있습니다.
개발 PC: YOLO 학습, Isaac Sim 시뮬레이션, 알고리즘 개발
엣지 디바이스: 카메라 입력, YOLO 추론, ROS 2 센서 처리, 경로 계획
로봇 컨트롤러: 모터 제어, 서보 루프, 안전 관련 기능 수행
이때 중요한 것은 엣지에서 모든 것을 실행하는 것이 아니라, 처리 지연·CPU/GPU 사용률·메모리·발열·통신 안정성을 고려하여 기능을 배분하는 것입니다. 일반적인 Linux/ROS 2 환경이 모든 제어 작업의 하드 실시간성을 보장하는 것은 아닙니다.

5. 실무적으로 학습해야 할 역량

엣지 로보틱스 분야를 준비한다면 ROS 2 시스템을 제한된 컴퓨팅 자원에 배포하고, 성능과 안정성을 정량적으로 검증하는 능력이 중요합니다.
특히 다음 순서가 효율적입니다.
Linux 시스템 자원 분석(CPU, RAM, I/O, 발열)
ROS 2 멀티노드 환경 구성과 DDS QoS 튜닝
AI 모델의 ONNX 변환 및 TensorRT 최적화
Docker 기반 ARM64/x86_64 배포
End-to-end latency, FPS, 전력 소비 측정
Watchdog, 장애 복구, 자동 재시작 구현
현재 보유한 Ubuntu PC나 Android + Termux 기기도 엣지 컴퓨팅 실습에 활용할 수 있습니다. 다만 Android는 기기·커널·드라이버 제약으로 ROS 2와 하드웨어 가속 지원이 제한될 수 있습니다.
한 가지 구분하면 좋겠습니다. 지금 궁금한 것이 엣지 디바이스의 일반적인 개념인지, 아니면 ROS 2·AI 로봇 시스템을 실제 엣지 장치에 배포하기 위한 개발 환경 구성인지에 따라 설명의 깊이와 방향이 달라집니다.
확신도: 검증됨(같은 턴 도구 출력으로 확인) / 추론(근거 있으나 미확인)
내가 채워넣은 가정: 로보틱스 기반 엣지 컴퓨팅 환경에 대한 질문으로 해석함.
확인 요청: 개념·직무 역량 중심인지, 실제 하드웨어 및 소프트웨어 환경 구축 중심인지?

Q2 · Jetson과 PC의 연산 분배

사용자 프롬프트 원문
그럼 기존에 pc 한대로 센서도 켜고 통신받아서 연산하던 기존 구조에서, jetson orin nano등에서 모델 처리 후 pc로 전송하여 판단하는 로직으로 구성할 수 있나? 그러면 리소스 및 데이터 병목을 분배해 문제를 개선할 수 있는건가
제공된 답변 원문
네. 기존 PC 한 대에서 수행하던 센서 처리·AI 추론·판단·제어 기능을 Jetson Orin Nano와 PC로 분산하는 구조는 충분히 가능합니다. 실제 로보틱스에서도 활용하는 분산 컴퓨팅(Distributed Computing) 아키텍처입니다.
특히 기존에 활용했던 ROS 2 + RealSense + YOLO + 로봇 제어 시스템을 기준으로 보면, Jetson에서 AI 추론을 수행하고 PC에서 결과를 받아 판단·제어하는 방식이 합리적인 설계가 될 수 있습니다.
다만 중요한 차이가 있습니다.
연산 부하 분산은 비교적 확실하게 기대할 수 있지만, 데이터 병목이나 전체 응답 지연이 개선되는지는 센서 데이터의 전송 위치, 네트워크 대역폭, 추론 성능에 따라 달라집니다.

2. 실제로 어떤 병목을 개선할 수 있는가?

병목 유형분산 구성 효과이유
PC GPU 점유율개선 가능YOLO 추론을 Jetson으로 이전

PC RAM 사용량개선 가능모델 메모리와 영상 버퍼 분리
USB 대역폭조건부 개선센서를 Jetson에 직접 연결한 경우
Ethernet 트래픽조건부 개선원본 영상 대신 인식 결과 전송
전체 추론 지연불확실Jetson이 기존 PC GPU보다 느릴 수 있음
시스템 신뢰성설계 의존네트워크 단절 등 장애 지점 추가
여기서 특히 중요한 것은 센서의 연결 위치입니다.
A. 카메라를 PC에 계속 연결하는 경우
Camera → PC → Ethernet → Jetson → Ethernet → PC
이 경우 PC에서 원본 영상을 받아 Jetson으로 전송해야 합니다. PC의 GPU 추론 부하는 줄어들지만 PC의 영상 I/O와 네트워크 부담은 오히려 커질 수 있습니다.
B. 카메라를 Jetson에 직접 연결하는 경우
Camera → Jetson(전처리 + AI) → Ethernet → PC(판단)
이 방식에서는 PC가 원본 영상을 받을 필요가 없습니다. Jetson이 추론한 결과만 전송하므로 연산 병목과 데이터 전송 병목을 동시에 줄일 가능성이 높습니다.

객체 검출 결과는 프레임당 10개 객체, 객체당 50바이트, 30FPS를 가정했습니다. 실제 메시지 크기는 다를 수 있습니다.
위 예시에서 원본 RGB 영상만 초당 약 187MB가 발생합니다. 반대로 객체 인식 결과는 수십~수백 바이트 수준의 메시지로 표현할 수 있습니다.
따라서 원본 영상 대신 좌표·클래스·신뢰도만 보내면 네트워크 사용량을 크게 줄일 수 있습니다. 다만 세그멘테이션 마스크, Depth Map, PointCloud2를 추가로 전송한다면 데이터 크기가 다시 커지므로 별도 설계가 필요합니다.

4. ROS 2에서는 어떻게 구성하는가?

ROS 2의 DDS 통신을 이용하면 Jetson과 PC가 별도 장치여도 동일한 ROS 2 시스템에 참여할 수 있습니다.
예를 들어 다음처럼 토픽을 분리합니다.
장치ROS 2 노드토픽
Jetsonrealsense_node/camera/color/image_raw (로컬 소비)
Jetsonyolo_inference_node/detections
PCperception_fusion_node/detections 구독
PCdecision_node/target_pose
PCmotion_planner_node/planned_trajectory
PCrobot_control_node/robot_command
센서 데이터의 QoS와 결과 메시지의 QoS도 구분해야 합니다. ROS 2는 Reliability, History, Depth 등의 정책을 지원합니다.
Design
이미지·고주기 센서 토픽: BEST_EFFORT + KEEP_LAST, 작은 큐를 고려
검출 결과 토픽: RELIABLE + KEEP_LAST 또는 최신 데이터 중심의 BEST_EFFORT를 요구사항에 따라 선택
모든 결과에 header.stamp, frame_id 포함
PC에서 수신한 결과의 유효기간(TTL)을 확인하고 오래된 결과 폐기
장애 시 감속·정지하는 Watchdog 구현
또한 동일한 DDS 도메인을 사용하더라도 방화벽, 멀티캐스트, DDS Discovery, RMW 호환성 등 네트워크 설정이 맞아야 통신이 이루어집니다.

5. 중요한 함정: Jetson을 추가해도 더 빨라지지 않을 수 있다

기존 PC에서 RTX 4060을 사용했다면, YOLO 추론을 Jetson Orin Nano로 이전한다고 해서 추론 속도가 빨라지는 것은 아닙니다.
Jetson Orin Nano Super의 공식 사양은 최대 67 INT8 TOPS, 8GB LPDDR5 메모리, 7~25W 전력 모드입니다.

흥미로운 점은 개별 추론 시간이 길어지더라도 전체 시스템의 동작이 더 안정적일 수 있다는 것입니다.
기존 PC에서 AI 추론이 CPU/GPU 자원을 계속 점유하여 경로 계획 노드의 실행 주기가 흔들렸다면, 추론 부하를 Jetson으로 분리함으로써 제어 판단 노드의 지터(jitter)를 줄일 가능성이 있습니다.
이때는 평균 FPS보다 E2E latency의 P95/P99, 제어 주기 지터, 프레임 누락률을 측정하는 것이 더 중요합니다.

Baseline 측정: 기존 PC에서 추론 FPS, E2E latency, CPU/GPU 사용량 및 ROS 2 제어 주기를 기록합니다.

성능 비교: 동일한 모델·입력 해상도·센서 주기 조건에서 병목 감소 및 제어 안정성 개선 여부를 확인합니다.
추가로 Jetson 측에서 추론 결과를 전송할 때는 원본 영상의 타임스탬프를 유지해야 합니다. 그렇지 않으면 PC에서 LiDAR와 카메라 데이터를 융합할 때 시간 불일치로 위치 오차가 발생할 수 있습니다.
결론
지금 생각한 방식은 단순히 연산 장치를 하나 더 설치하는 것을 넘어, 실시간 센서 처리와 고부하 AI 추론을 분리하여 로봇 시스템의 자원 경합(Resource Contention)을 줄이는 아키텍처 개선입니다.
특히 AMR 및 협동로봇에서는 충분히 검토할 가치가 있습니다. 다만 보유 PC의 GPU가 Jetson보다 강력한 경우에는 최대 추론 성능보다 자원 격리, 제어 주기 안정화, 현장 배포성 및 장애 대응을 목표로 설계하는 편이 합리적입니다.

다만 실제 로보틱스 제품에서는 한 단계 더 나아갑니다. 단순한 연산 성능 최적화가 아니라 기능별 책임 분리, 실시간성 보장, 고장 격리(Fault Isolation), 안전성 확보를 위해 하드웨어 아키텍처를 설계합니다.

1. 물리적 분산 (Distributed Computing)

Jetson과 PC처럼 서로 다른 장치에서 노드를 실행하는 것입니다. 전력·발열·메모리·I/O 자원을 물리적으로 분리합니다.

2. 논리적 분리 (Modular Architecture)

한 대의 PC에서도 ROS 2 노드, 별도 프로세스, CPU Affinity, 프로세스 우선순위 등으로 기능을 격리할 수 있습니다.

3. 시간적 분리 (Real-time Isolation)

일반 Linux에서 실행하는 AI 추론과 엄격한 실행 주기가 필요한 제어 루프를 분리하는 것입니다. 경우에 따라 실시간 OS, 별도 MCU, RT Linux 등을 사용합니다.
이 세 가지는 서로 다른 개념이지만 실제 제품에서는 함께 적용됩니다.

4. 실무에서 더 중요한 아키텍처 설계 기준

단순히 PC 성능이 부족해서 Jetson을 추가하는 접근보다 다음 기준으로 장치를 배정하는 편이 좋습니다.

장애 시에도 유지해야 할 기능독립 컨트롤러와 Watchdog 설계
로봇 외부에서 처리해도 되는 작업서버·클라우드 활용
이때 무조건 분산하는 것이 유리한 것은 아닙니다. 노드가 서로 초당 수백 회씩 대용량 데이터를 주고받는다면, 장치 사이로 분리했을 때 통신과 직렬화 비용이 증가할 수 있습니다.
반대로 AI 추론 결과처럼 작고 의미 있는 데이터만 전송하는 경우에는 분산 효과가 큽니다.
